# OAuth сторонние аккаунты

Статус: **спроектировано, код не написан** (по просьбе пользователя — вход
через ВК/Google/Яндекс сейчас только архитектура, без живого подключения; см.
уточняющий ответ "Спроектировать архитектуру сейчас (рекомендую)").
Зависит от: [[Class_Internet]], [[Class_InternetServer]], [[Class_InternetClient]],
[[Сцена Start_Program]] (заглушки кнопок `AccountPickerOAuthVkButton`/
`...GoogleButton`/`...YandexButton`)

## Почему не подключено сейчас
Любой OAuth-провайдер (ВКонтакте, Google, Яндекс) требует, чтобы РАЗРАБОТЧИК
заранее зарегистрировал приложение в консоли этого провайдера и получил
`client_id` (публичный) и, для некоторых сценариев, `client_secret`
(секретный — не должен попадать в клиентский код вообще, только на сервер).
Это может сделать только сам владелец проекта — данные для входа в консоли
ВК/Google/Яндекс отсутствуют, и подставлять в код тестовые/чужие значения
означало бы либо нерабочую заглушку, либо чужой аккаунт разработчика. Поэтому
сейчас — только архитектура: что нужно добавить в протокол и куда именно
вставить провайдерский `client_id`, когда он появится.

## Общая идея — сервер валидирует, не клиент
Каждый провайдер даёт токен подтверждения личности (Google/Яндекс — ID-токен
формата JWT, либо код авторизации, который сервер меняет на токен;
ВКонтакте — свой формат, VK ID / silent-token). Клиент НЕ должен сам решать
"пользователь тот, за кого себя выдаёт" — эту проверку обязан делать сервер,
обратившись к самому провайдеру (иначе клиент мог бы подделать любой ответ).
Общая схема:

1. Пользователь нажимает "Войти через ВК/Google/Яндекс".
2. Приложение открывает системный браузер на странице авторизации провайдера
   (Godot: `OS.shell_open(url)` — открывает URL во внешнем браузере, не внутри
   игры; десктопное Godot-приложение не встраивает веб-вью из коробки).
3. Провайдер после согласия пользователя перенаправляет на заранее
   зарегистрированный redirect URI. Для десктоп-приложения без своего сервера
   это либо (а) локальный HTTP-листенер на `127.0.0.1:<порт>`, который
   Start_Program поднимает временно на время входа и слушает один редирект
   (стандартный паттерн для десктоп/CLI OAuth-клиентов — "loopback redirect",
   его использует и `gcloud`, и многие desktop-приложения), либо (б)
   Device Authorization Grant (там, где провайдер его поддерживает — вводится
   код на отдельной странице, приложению редирект не нужен вообще). Выбор
   между (а)/(б) — за разработчиком в момент реального подключения, зависит
   от того, что предлагает конкретный провайдер.
4. Приложение получает код/токен из редиректа и пересылает его СЕРВЕРУ (не
   пытается провалидировать сторонний токен само) — новая операция
   `Op = "OAuthLogin"`, `Messages = {"Provider": "VK"/"Google"/"Yandex",
   "Code"/"IdToken": "..."}`.
5. Сервер обращается к API провайдера (HTTP-запрос — Godot: `HTTPRequest`)
   и получает подтверждённый внешний идентификатор пользователя
   (`sub`/`user_id`, в зависимости от провайдера) — либо проверяет подпись
   JWT локально (Google/Яндекс ID-токены подписаны, проверка возможна без
   сетевого запроса, если есть публичные ключи провайдера — усложнение на
   будущее, для первой версии проще сходить в API провайдера напрямую).
6. Сервер ищет в `Users.json`, есть ли уже аккаунт, привязанный к этому
   `(Provider, ExternalID)`. Если да — обычный `AuthSuccess` с `Token`, как
   после challenge-response. Если нет — либо создаёт новый аккаунт
   автоматически (по аналогии с `fC_RegisterUser_Ch`, но без пароля — только
   привязка к провайдеру), либо (если пользователь уже вошёл под обычным
   логином/паролем) предлагает ПРИВЯЗАТЬ провайдера к текущему аккаунту —
   конкретное поведение решается позже, это развилка продукта, не только кода.

## Изменения в хранилище пользователей (когда дойдёт до реализации)
`Users.json` (см. [[Class_InternetServer#Хранилище пользователей]]) — добавить
необязательное поле:
```
{
	"Логин1": {
		"PasswordHash": "...", "Salt": "...", "CreatedAt": ...,
		"OAuthLinks": {"VK": "внешний_id", "Google": "внешний_id"}
	}
}
```
Пароль остаётся необязательным — аккаунт, заведённый ТОЛЬКО через OAuth (без
своего пароля), просто не может логиниться обычным challenge-response, только
через привязанного провайдера.

## Изменения в протоколе (когда дойдёт до реализации)
- Новая операция `Op = "OAuthLogin"` — по аналогии с `Op = "Register"` (см.
  [[Class_InternetServer#Самостоятельная регистрация — новая операция `Register`]]),
  тоже требует WSS (внешний код авторизации/токен провайдера — не менее
  чувствительные данные, чем пароль).
- Ответ `"OAuthLoginResult"` — либо `AuthSuccess`-подобный (`{Ok:true, Token,
  KeepAliveTimeoutSeconds}`), либо `{Ok:false, Error}`.
- На стороне `Class_InternetClient` — новая функция `fC_LoginWithOAuth_Ch(vGS_Provider_S,
  vGS_CodeOrToken_S)`, по образцу уже написанной `fC_RegisterAccount_Ch`
  (см. [[Class_InternetClient#Правка 2026-08-24]]) — тот же принцип: ответ идёт
  через `AppOpReceived_S`, отдельный `case` в `ReceivingNotification` не нужен.
- На стороне `Start_Program.gd` — три кнопки-заглушки уже существуют
  (`AccountPickerOAuthVkButton`/`...GoogleButton`/`...YandexButton`, см.
  [[Сцена Start_Program]]), сейчас просто показывают информационное сообщение
  (`_fC_OnOAuthButtonPressed_Ch`) — когда появятся реальные `client_id`, их
  обработчик меняется на реальный запуск шага 2 схемы выше.

## Где хранить client_id/client_secret, когда они появятся
- `client_id` (публичный, ВК/Google/Яндекс все его считают несекретным) —
  можно держать в коде клиента (как константу, по аналогии с `SERVER_ADDRESS_S`)
  или в конфиге.
- `client_secret` (если провайдер его требует для конкретного flow) —
  **только на сервере**, никогда в клиентском коде/репозитории игры. Через
  переменные окружения запуска глобального сервера или отдельный
  незакоммиченный файл — тот же принцип, что уже принят в проекте для
  `Users.json` (реальные данные — плоским текстом локально, не в общий
  репозиторий; секреты провайдеров — тем более).

## Открытые вопросы (нерешаемые без реальных учётных данных провайдера)
- Какой именно flow предложит каждый провайдер в 2026 году для десктоп-
  приложений без своего backend-URL (у ВК/Google/Яндекс это периодически
  меняется — стоит сверяться с актуальной документацией провайдера в момент
  реализации, а не полагаться на этот документ как на факт).
- Порт для локального loopback-листенера — фиксированный (риск конфликта с
  другим ПО на устройстве пользователя) или занимаемый динамически
  (сложнее — провайдер должен принять "любой localhost-порт" в настройках
  redirect URI, не все это разрешают).
- Продуктовое решение "автосоздание аккаунта по первому OAuth-входу" vs.
  "обязательная привязка к уже созданному логину/паролю" — см. шаг 6 схемы
  выше, это не технический, а продуктовый вопрос.
