# Class_FileIntegrity

Путь: `res://Class/Class_FileIntegrity.gd`
Наследует: `RefCounted`
Класс: `Class_FileIntegrity`
Версия оформления в файле: 0.1.1.0

## Для чего нужен
Общая логика для проверки `"ThirdPartyFiles"` (см. [[Class_Internet]] → «После установления соединения: проверки Update/ThirdPartyFiles») — переиспользуется и клиентом ([[Сцена Start_Program]] — строит отпечатки, что слать серверу), и сервером (`test.gd` — строит manifest И проверяет присланные отпечатки). Все функции `static` — вызывать напрямую как `Class_FileIntegrity.fC_...`, без `load(...).new()`.

⚠️ Отпечаток — размер + первый/последний БАЙТ + один случайный байт (со своим индексом, выбирается заново при каждом вызове [[#fC_BuildFingerprint_Cr]]) — спот-проверка, а не полный хеш, так задано в постановке задачи от пользователя. Байты, а не символы: `PackedByteArray` индексируется по байтам, а один байт многобайтовой UTF-8-последовательности — не самостоятельный символ; раз обе стороны читают одни и те же сырые байты одним и тем же способом, для СРАВНЕНИЯ (не для отображения текста) это ничем не хуже символов и проще.

⚠️ Код не запускался живьём в Godot.

## Переменные

### EXCLUDED_PREFIXES_A
`const Array` — префиксы путей, которые НЕ считаются частью проверяемого набора: `["res://Save/", "res://.godot/", "res://.import/", "res://.git/"]`. `Save/` — индивидуальные/пер-инсталляционные данные (настройки, сохранения, логи, список аккаунтов, серверная БД пользователей); остальные три — служебные папки, которых нет в собранной игре, но которые видны через `res://`, пока проект запущен не из экспорта.

## Функции

### fC_ListCheckableFiles_Cr(vGS_Root_S = "res://")
- Назначение: рекурсивно обойти `res://` (или указанный корень) и вернуть список путей файлов, которые подлежат проверке целостности.
- Входные данные: `vGS_Root_S: String` — с чего начать (по умолчанию `"res://"`).
- Выходные данные: `Array` — `res://`-пути (`String`), см. [[#EXCLUDED_PREFIXES_A]].
- Принцип работы: рекурсивный обход через `DirAccess` (служебная `_fL_WalkDirectory_Ch`), пропускает пути, начинающиеся с любого из [[#EXCLUDED_PREFIXES_A]].
- ⚠️ "Все не индивидуальные" — сегодняшний охват (см. открытый вопрос в [[Class_Internet]] про сужение до "известных серверу" позже).

### fC_BuildFingerprint_Cr(vGS_Path_S)
- Назначение: прочитать файл целиком и построить его "отпечаток" для отправки на проверку.
- Входные данные: `vGS_Path_S: String`.
- Выходные данные: `Dictionary` — `{"Path","Size","FirstByte","LastByte","RandomIndex","RandomByte"}`, или `{}` **только если файла реально нет**. Для существующего, но пустого (0 байт) файла — честная запись с `Size=0`, `FirstByte`/`LastByte`/`RandomIndex`/`RandomByte` = `-1` (сентинел, индексировать нечего).
- Принцип работы: сначала проверяет `FileAccess.file_exists()`; если файл есть, читает как `PackedByteArray`, выбирает случайный индекс (`randi() % Size`), собирает словарь с размером, первым/последним байтом и случайным байтом+индексом.
- ⚠️ **2026-08-24, найден и починен баг** (при ревью интернет-кода по просьбе пользователя): раньше `{}` возвращалось при `is_empty()` прочитанных байт — а это условие истинно и для отсутствующего файла, и для файла в 0 байт, `FileAccess.get_file_as_bytes()` в обоих случаях даёт пустой массив. Из-за этого посторонний мог ОПУСТОШИТЬ (усечь до 0 байт) уже отслеживаемый файл — вместо честного `Mismatch` (несовпадение размера с manifest) отпечаток такого файла просто ВЫПАДАЛ из списка, который [[Сцена Start_Program]]`::_fC_SendFileIntegrityCheckRequest_Ch` отправляет на проверку (берёт только непустые словари) — то есть файл исчезал из проверки целиком. Теперь функция явно отличает "файла нет" от "файл есть, но пустой".

### fC_BuildManifestEntry_Cr(vGS_Path_S)
- Назначение: построить статическую запись manifest'а для одного файла (используется сервером при пересборке `FileManifest.json`, см. `test.gd` → `fC_RegenerateFileManifest_Ch`).
- Входные данные: `vGS_Path_S: String`.
- Выходные данные: `Dictionary` — `{"Size","FirstByte","LastByte"}` (БЕЗ случайного байта — тот выбирается заново каждой проверкой на стороне клиента), или `{}` **только если файла реально нет** (для пустого-но-существующего — `Size=0`, `FirstByte`/`LastByte` = `-1`, та же правка 2026-08-24, что и у [[#fC_BuildFingerprint_Cr]]).
- Отличие от [[#fC_BuildFingerprint_Cr]]: не содержит `Path`/`RandomIndex`/`RandomByte` — эта запись хранится в manifest под ключом-путём, а случайный байт статично не хранится вообще (см. [[Class_Internet]] → «Проверка "ThirdPartyFiles"» — сервер читает его "живьём").

### fC_ReadByteAt_I(vGS_Path_S, vGI_Index_I)
- Назначение: серверная сторона — прочитать РЕАЛЬНЫЙ файл и вернуть байт по указанному индексу, для проверки случайного байта, присланного клиентом ("нахождение символов" из постановки задачи).
- Входные данные: `vGS_Path_S: String`; `vGI_Index_I: int`.
- Выходные данные: `int` (0..255) — байт по индексу; `-1`, если индекс вне диапазона/файл не прочитать (никогда не совпадёт с настоящим байтом — безопасное значение "точно не совпало").
- Принцип работы: в текущей dev-схеме сервер работает из того же проекта, что и клиент (см. `test.gd`), поэтому читает файл напрямую с диска сервера — заранее хранить в manifest ответы на ВСЕ возможные случайные позиции нереалистично.

## Открытые вопросы
- Список исключаемых путей ([[#EXCLUDED_PREFIXES_A]]) не тестировался на реальном экспортированном билде — возможны файлы, которые видны при запуске из редактора/исходников, но которых не будет в сборке (или наоборот) — см. [[Class_Internet]] → «Открытые вопросы».
- Static-функции читают файл с диска на каждый вызов ([[#fC_BuildFingerprint_Cr]]/[[#fC_BuildManifestEntry_Cr]]/[[#fC_ReadByteAt_I]] всегда открывают файл заново) — для большого количества файлов может быть медленно; пока не оптимизировалось, целостность важнее скорости на этом этапе.
