# Class_InternetClient

Путь: `res://Class/Class_InternetClient.gd`
Наследует: `Class_Internet` (не `Node` напрямую — общие функции отправки/ожидания ответа берутся из родителя, см. [[Class_Internet]])
Класс: `Class_InternetClient`
Статус: **спроектировано, код не написан**
Зависит от: [[Class_Internet]] (родитель — `SendingMessage`/`WaitingResponse`, формат сообщения, открытые вопросы по адресации)

## Для чего нужен
Клиентская сторона обмена сообщениями — не важно, локальный это сервер, поднятый другим игроком, или глобальный официальный сервер (см. [[Class_InternetServer]]). Общие с сервером функции (`SendingMessage`, `WaitingResponse`) не переопределяются — используются как есть из [[Class_Internet]]. Здесь — только то, что у клиента своё: как оно устанавливает соединение и как обрабатывает то, что пришло.

## Функции (переопределяют форму, объявленную в [[Class_Internet]])

### EstablishingConnection(UserID, Messages, Time, AnswerTo, RecipientID)
- Назначение: клиентская сторона установки соединения — набрать известный адрес сервера и представиться.
- Принцип работы:
	1. Открывает транспорт по известному адресу (`RecipientID`/`RecipientIP` — адрес сервера, к которому подключаемся, единственный случай у клиента, когда нужен именно IP, а не ID, — см. [[Class_Internet#Формат сообщения]]; сервер игрока или официальный глобальный — с точки зрения этой функции разницы нет, отличается только то, ЧТО подставлено сюда).
	2. Как только транспорт открылся — отправляет `Hello` через [[Class_Internet#SendingMessage]] с `Op = "Hello"` (никакого отдельного протокола подключения нет — соединение и правда физически строится через ту же функцию отправки сообщения, что и всё остальное; то, что различается у клиента и сервера, — это КОГДА и с какими данными она вызывается, а не сама функция отправки).
	3. Ждёт ответ (через [[Class_Internet#WaitingResponse]]) — в нём должны прийти назначенный сервером идентификатор соединения и серверное время (для первой синхронизации, см. [[Class_Internet#Пинг и синхронизация времени]]); если сервер требует авторизацию (только глобальный сервер, см. [[Class_InternetServer#Авторизация]]) — где именно в этой цепочке уходят логин/пароль, ещё не зафиксировано (см. «Открытые вопросы»).

### ReceivingNotification(UserID, Op, Messages, Time, AnswerTo)
- Назначение: обработка того, что прислал сервер.
- Принцип работы: по твоей формулировке — через `match` по `Op` (у клиента заметно меньше видов входящих сообщений, чем у сервера, поэтому `match` выглядит достаточным, в отличие от сервера, где вероятнее диспетчер по словарю — см. [[Class_InternetServer#ReceivingNotification]]). Дальше, если `AnswerTo` пусто (то есть сервер сам инициировал сообщение — push, а не ответ на наш запрос), клиент отвечает подтверждением получения через [[Class_Internet#SendingMessage]].

## Реконнект при смене сети
Не отдельная функция из твоего списка, а надстройка НАД уже описанным: если транспорт разорвался целиком (не единичное сообщение потерялось — это уже покрыто `ForwardingTimeArray` в [[Class_Internet#WaitingResponse]] — а именно всё соединение отвалилось), клиент заново вызывает [[#EstablishingConnection]] с задержкой (например по тому же принципу, что и `ForwardingTimeArray` — заранее посчитанный массив моментов повтора, а не жёстко зашитый таймер). После успешного повторного `EstablishingConnection` всё, что оставалось в ожидании ответа через `WaitingResponse`, само досылается по своему расписанию — отдельная очередь на реконнект не нужна, если `WaitingResponse` и так уже умеет повторять отправку.

## Правка 2026-08-24 (по просьбе пользователя: шифрование + самостоятельная регистрация)
См. [[Class_InternetServer#Правка 2026-08-24 (по просьбе пользователя: шифрование + самостоятельная регистрация)]] — здесь только клиентская половина того же уточнения объёма.

### TLS (WSS) — опция
- `vG_TlsOptions_L: TLSOptions = null` — выставляется СНАРУЖИ (`Start_Program.gd`, если адрес сервера начинается с `wss://`) ДО вызова `EstablishingConnection`. `null` — обычное нешифрованное соединение, поведение не меняется.
- `EstablishingConnection` передаёт его вторым параметром в `WebSocketPeer.connect_to_url(url, tls_client_options)` — в отличие от сервера, клиенту не нужен отдельный цикл ожидания TLS-рукопожатия, это делает сам `WebSocketPeer` внутри себя.

### Самостоятельная регистрация — `fC_RegisterAccount_Ch(vGS_Login, vGS_Password)`
- Точка входа для UI регистрации (аналогично уже существующей `fC_SendCredentials_Ch` для входа) — вызывается снаружи, пока клиент в `ConnectionState.AUTHENTICATING`. Шлёт `Op="Register"` с `{Login, Password}` через `SendingMessage` (`AnswerNeeded=true`).
- Ответ (`"RegisterResult"`) НЕ получил отдельного `case` в `ReceivingNotification` — как и любая другая прикладная операция (`CheckUpdate`/`CheckFiles`), он проходит через default-ветку резолва и попадает в `AppOpReceived_S` (см. правку 2026-08-23 про `AppOpReceived_S` в [[Class_Internet]]) — обрабатывается в `Start_Program.gd::_fC_HandleRegisterResult_Ch`.
- ⚠️ В отличие от обычного входа (challenge-response — пароль по сети НЕ передаётся), при регистрации пароль уходит на сервер напрямую одним пакетом: на этапе регистрации ещё нет общего секрета для challenge, поэтому этот единственный пакет должен идти по WSS (см. `vG_TlsOptions_L` выше), иначе пароль виден в открытом виде.
- ⚠️ Не проверялось живьём.

## Открытые вопросы
- Где именно в хендшейке уходят логин/пароль для глобального сервера — вместе с `Hello` или отдельным сообщением сразу после (см. также [[Class_InternetServer#Авторизация]]).
- Нужен ли отдельный heartbeat (лёгкое сообщение «ты тут?», когда обычного трафика долго нет), или ожидания ответа на обычные сообщения хватает, чтобы вовремя заметить обрыв — раньше предполагался отдельный `fC_HeartbeatPing_Ch`, сейчас неочевидно, нужен ли он при уже описанном `WaitingResponse`.
- Общие вопросы по формату/адресации — см. [[Class_Internet#Открытые вопросы]] (устройство таблицы активных подключений, название `OperationNumber`, транспорт).
