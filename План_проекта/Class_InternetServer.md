# Class_InternetServer

Путь: `res://Class/Class_InternetServer.gd`
Наследует: `Class_Internet` (не `Node` напрямую — общие функции отправки/ожидания ответа берутся из родителя, см. [[Class_Internet]])
Класс: `Class_InternetServer`
Статус: **спроектировано, код не написан**
Зависит от: [[Class_Internet]] (родитель), [[Class_Json]] (файл пользователей, см. «Авторизация»)

## Для чего нужен
Серверная сторона того же протокола, что и [[Class_InternetClient]] — общие функции (`SendingMessage`, `WaitingResponse`) не переопределяются, берутся из [[Class_Internet]] как есть.

Важное отличие от обычных серверных классов: этот же класс должен уметь запускаться ДВУМЯ способами из одного и того же кода —
1. **Сервер игрока** — поднимается прямо внутри работающего клиентского процесса, когда игрок нажимает «Создать сервер» в интерфейсе (тот же процесс — и клиент, и хост одновременно, «host and play»).
2. **Глобальный сервер** — тот же класс, запущенный headless-сборкой (без единой UI-ноды) на отдельной машине/VPS.

Отсюда — авторизация (см. ниже) включается флагом, а не встроена в протокол обязательным требованием: у сервера игрока учёток обычно нет, у глобального — есть.

## Функции (переопределяют форму, объявленную в [[Class_Internet]])

### EstablishingConnection(UserID, Messages, Time, AnswerTo, RecipientID)
- Назначение: серверная сторона установки соединения — реакция на входящее подключение (в отличие от клиента, здесь сторона не «набирает номер», а принимает входящий вызов).
- Принцип работы:
	1. Принимает входящее TCP/WebSocket-подключение, `RecipientID` здесь ещё не известен — появится только на следующем шаге.
	2. Назначает `UserID`/идентификатор соединения этой линии связи и заносит её в таблицу активных подключений (`UserID/ConnectionID → IP/сокет`) — именно эта таблица отвечает на вопрос из [[Class_Internet#Формат сообщения]] «как достать IP по ID» (подробное устройство таблицы — открытый вопрос, см. ниже). Заодно фиксирует реальный IP подключившегося отдельно (для логов/анти-абьюза).
	3. Отвечает `Hello` через [[Class_Internet#SendingMessage]] с `Op = "Hello"` (идентификатор соединения, серверное время для первой синхронизации, флаг `RequireAuth`).
	4. Ждёт подтверждения через [[Class_Internet#WaitingResponse]] — если `RequireAuth` включён, подтверждение должно содержать логин/пароль (см. «Авторизация»); если клиент не ответил после исчерпания `ForwardingTimeArray` — соединение закрывается, из таблицы активных подключений убирается (тот же принцип ограниченного числа попыток, что уже есть в проекте — `AutoClickDodgeLimit` в `Start_Program.gd`).
	5. При `RequireAuth` — проверяет логин/пароль (`fC_ValidateCredentials_Bv`, см. «Авторизация»); неверные — отвечает ошибкой и закрывает соединение.

### ReceivingNotification(UserID, Op, Messages, Time, AnswerTo)
- Назначение: обработка входящего запроса от уже подключённого клиента — здесь же живёт вся трекерная логика операций (какие именно операции понадобятся — определится по ходу дела).
- Принцип работы: по твоей формулировке — через диспетчер (`if`/словарь `{Op: Callable}`, тот же generic-паттерн, что уже используется в `Start_Program.gd` для сигналов UI, просто теперь по сетевой операции, а не по сигналу кнопки) — у сервера ожидается заметно больше видов входящих сообщений, чем у клиента (см. [[Class_InternetClient#ReceivingNotification]]), поэтому `match` тут менее удобен. Обработчик формирует ответ и отправляет его через [[Class_Internet#SendingMessage]] с `AnswerTo`, указывающим на исходное сообщение (`{UserID, Time, OperationNumber}`, см. [[Class_Internet#Формирование `AnswerTo`]]).

## Авторизация
Только для режима `RequireAuth = true` (глобальный сервер) — сервер игрока по умолчанию без учёток.

### Хранилище пользователей
Черновая структура (через [[Class_Json]], например `Save/Server/Users.json`):
```
{
	"Логин1": {"PasswordHash": "...", "Salt": "...", "CreatedAt": <unix_время>},
	"Логин2": {...}
}
```

#### fC_RegisterUser_Ch(vGS_Login, vGS_Password) *(рабочее имя, регистрация — отдельная операция, не часть хендшейка)*
- Назначение: завести нового пользователя — генерирует `Salt`, хеширует пароль (`PasswordHash = SHA256(Salt+Password)`), сохраняет через [[Class_Json]]. Сейчас единственный способ появления новой записи — ВРУЧНУЮ (см. правку 2026-08-23 ниже), сам хендшейк новых пользователей не заводит.

⚠️ **Пароль ни в каком виде не хранится и не логируется в открытом тексте** — только соль + хеш.

### Хендшейк входа — challenge-response + токен (2026-08-23, решено, подробности в [[Class_Internet#Авторизация: challenge-response + токен]])
Заменяет прежнюю идею «подтверждение сразу содержит логин/пароль» — вместо этого три шага поверх уже существующих `SendingMessage`/`WaitingResponse`/`ReceivingNotification`, без отдельного протокола:

#### _fL_OnAuthRequest_Ch(vGS_ConnId, vGS_Login)
- Назначение: реакция на `Op="AuthRequest"` — начало входа.
- Принцип работы: генерирует случайный `Challenge` (`Crypto.generate_random_bytes`, как и соль при регистрации), запоминает его привязанным к `vGS_ConnId` (недолго — до следующей попытки или таймаута), отвечает `Op="Challenge"` с `{Challenge, Salt}` через `SendingMessage` с `AnswerNeeded=true`.

#### fC_ValidateChallengeResponse_Bv(vGS_Login, vGS_Response, vGS_Challenge)
- Назначение: проверить ответ клиента на `Challenge` — заменяет прежнюю `fC_ValidateCredentials_Bv` (пароль в открытом виде на вход больше не подаётся).
- Принцип работы: находит `PasswordHash` этого `Login`, считает `SHA256(PasswordHash + Challenge)`, сравнивает с присланным `Response`. См. [[Class_Internet#Авторизация: challenge-response + токен]] про то, почему это работает, и про осознанное ограничение схемы (кража `Users.json` эквивалентна знанию пароля для входа).

#### _fL_OnHelloConfirm_Ch — переработана
- При успешной проверке: генерирует `Token` (случайная строка через `Crypto`), сохраняет `{Token → UserID}` в таблице токенов, ПРОМОУТИРУЕТ соединение с `ConnId`-адресации на адресацию по настоящему `UserID` (см. «Смена IP» ниже — если под этим `UserID` уже была другая активная запись, она заменяется), отвечает `Op="AuthSuccess"` с `{Token, KeepAliveTimeoutSeconds}`.
- При неуспехе — ошибка, соединение закрывается (как и раньше).

#### fC_ValidateToken_Bv(vGS_UserID, vGS_Token)
- Назначение: на КАЖДОМ последующем сообщении (когда `RequireAuth=true`) проверяет, что присланный `Token` соответствует тому, что выдан этому `UserID` — дешёвая проверка вместо повторного challenge-response.

## Правка 2026-08-23 (уточнение протокола, см. [[Class_Internet#Правка 2026-08-23 (уточнение протокола после первого черновика кода)]])
- Первое сообщение от клиента теперь явно несёт `UserID` + `IP` (а не только вычисляется сервером из сокета) — сервер отвечает, нужен ли пароль.
- Если `UserID` новый — по-хорошему нужно завести аккаунт, но это ОТКЛАДЫВАЕМ: пока такие пользователи дозаписываются в `Save/Server/Users.json` вручную, автоматической регистрации по первому подключению не делаем.
- **Смена IP у активного пользователя при переподключении — решено:** если уже АВТОРИЗОВАННЫЙ `UserID` подключается заново (новый сокет, возможно новый IP), сервер должен ОБНОВИТЬ его запись в таблице активных подключений на новое соединение, а не завести дубликат и не потерять пользователя. Это снимает прежний открытый вопрос «таблица активных подключений при реконнекте» ниже — ответ: да, сервер сам за это отвечает, а не только клиент через свой `WaitingResponse`.
- После установки соединения сервер должен явно сообщить клиенту, сколько времени он будет считать соединение живым БЕЗ повторного подтверждения — то есть добавить в ответ (`Hello` или отдельное сообщение сразу после) поле-таймаут; если это время истекло без вообще каких-либо сообщений от собеседника, соединение считается разорванным ДАЖЕ если сокет ещё формально `STATE_OPEN` (отдельная, более жёсткая проверка сверх обычного `ForwardingTimeArray` — тот про ОДНО сообщение, этот про соединение целиком без всякой активности).

## Правка 2026-08-24 (по просьбе пользователя: шифрование + самостоятельная регистрация)
Пользователь уточнил объём: «шифрование» = реальный TLS (WSS) как ОПЦИЯ на стороне сервера (не самодельное шифрование поверх сообщений); самостоятельную регистрацию (логин/пароль) — делать сейчас; вход через сторонние аккаунты (ВК/Google/Яндекс) — только спроектировать архитектуру, без живого подключения (см. [[Class_InternetClient#Правка 2026-08-24]] и «OAuth сторонние аккаунты»).

### TLS (WSS) — опция
- `vGB_UseTls_Bv: bool = false` — по умолчанию выключено, ничего не меняется для существующих серверов/тестов.
- `fC_ConfigureTls_Bv(vGS_CertPath_S, vGS_KeyPath_S) -> bool` — грузит ключ/сертификат (`CryptoKey`/`X509Certificate`), строит `TLSOptions.server(...)`, включает `vGB_UseTls_Bv`. Вызывается снаружи (например `test.gd`) ДО того, как сервер начинает принимать соединения — сама `Class_InternetServer` сертификаты не генерирует и не ищет сама.
- `_fL_OnClientStreamAccepted_Ch` теперь при `vGB_UseTls_Bv=true` не сразу открывает WebSocket поверх сырого `StreamPeerTCP`, а сначала запускает `StreamPeerTLS.accept_stream(...)` — асинхронное серверное TLS-рукопожатие, которое нужно опрашивать (`poll()`) каждый кадр, пока не станет `STATUS_CONNECTED`/`STATUS_ERROR*`. Для этого добавлен `vGD_PendingTlsConnections_D` — отдельная промежуточная стадия ПЕРЕД уже существующей `vGD_PendingConnections_D` (ожидание WS-рукопожатия): TLS-рукопожатие сначала, WS-рукопожатие поверх готового TLS-потока — второе полностью переиспользует уже написанный код (`WebSocketPeer.accept_stream` одинаково принимает что `StreamPeerTCP`, что готовый `StreamPeerTLS`).
- Для клиентов это прозрачно на уровне протокола — единственное отличие: адрес подключения `wss://...` вместо `ws://...` (см. [[Class_InternetClient#Правка 2026-08-24]]).
- ⚠️ Не проверялось живьём (нет сертификата под рукой в этой среде) — логика построена по документированному Godot 4 API (`StreamPeerTLS`/`TLSOptions.server`), но заслуживает реального теста с самоподписанным сертификатом прежде чем полагаться на неё в проде.

### Самостоятельная регистрация — новая операция `Register`
- `_fL_OnRegisterRequest_Ch(vGS_RoutingKey_S, vGD_Envelope_D)` — новый `case` в `ReceivingNotification` (`Op = "Register"`, `Messages = {Login, Password}`). Проверяет по порядку: `vGB_RequireAuth_Bv` включён (иначе регистрация не имеет смысла — сервер без авторизации), логин непустой и пароль не короче 4 символов, логин не зарезервирован (`SERVER_SELF_USERID_S`), логин ещё не занят (`Users.json`). При успехе — `fC_RegisterUser_Ch` (уже существовавшая функция, раньше вызывалась только вручную, см. правку 2026-08-23 выше) заводит пользователя, ответ `Op="RegisterResult"` с `{Ok, Error}`.
- Регистрация НЕ логинит автоматически — она только заводит запись в `Users.json`. Дальше клиент как обычно проходит `AuthRequest → Challenge → HelloConfirm` под только что зарегистрированными логином/паролем (см. `Start_Program.gd::_fC_HandleRegisterResult_Ch` — при успехе просто пускает обычный вход на следующем кадре).
- ⚠️ Пароль при регистрации приходит ОДНИМ ПАКЕТОМ В ОТКРЫТОМ ВИДЕ (в отличие от обычного входа — там challenge-response, пароль по сети не передаётся никогда) — именно поэтому регистрация обязательно требует WSS (см. выше), иначе пароль виден любому, кто слушает трафик.
- ⚠️ Не проверялось живьём — верифицировано только статически (баланс скобок, отсутствие дублей функций).

## Открытые вопросы
- **Хеш пароля.** В Godot из коробки есть `HashingContext`/`Crypto` (SHA-256 и т.п.), но нет медленного KDF (bcrypt/argon2/scrypt), который обычно рекомендуют именно для паролей. Предлагаю SHA-256 + случайная соль на пользователя как прагматичный минимум сейчас, с пометкой, что это не «золотой стандарт».
- ~~Таблица активных подключений при реконнекте — не решено~~ — **решено 2026-08-23**, см. правку выше: сервер сам обновляет запись активного подключения при смене IP/сокета у уже известного `UserID`.
- **Сервер игрока и NAT.** Если у сервера игрока обычный домашний роутер — снаружи (не из локальной сети) он может быть недоступен без ручного проброса порта. Если понадобится подключение не по локальной сети — либо инструкция игроку по пробросу порта, либо ретрансляция через глобальный сервер.
- Общие вопросы по формату/адресации — см. [[Class_Internet#Открытые вопросы]].
