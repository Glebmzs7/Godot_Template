# Инструкция: работа с Git в проектах (Godot_Template / Power_struggle / Life_Operator)

Черновик для проверки. Ничего из этого файла не применяется к репозиториям автоматически —
только после того, как вы скажете «Применяй» и укажете, в какой репозиторий класть файл.

## 1. Структура: шаблон + проекты-потребители

- **Godot_Template** — репозиторий-шаблон. Содержит общий код (`Сам проект/Godot_Template/`),
  план проекта и требования. Полная политика веток — в `BRANCHES.md` в его корне.
- **Life_Operator**, **Power_struggle** — проекты-потребители. Тянут общий код шаблона к себе
  через `git subtree` (remote `godot-template` → репозиторий Godot_Template, ветка
  `export/Stable` или `export/Beta`). Команды — в `Сам проект/Godot_Template/UPDATING.md`
  внутри каждого проекта-потребителя.

Важно: `Power_struggle` — репозиторий склонирован не в корне папки проекта, а внутри
`Сам проект/` (`Сам проект/.git`), поэтому путь до общего кода там без пробела —
просто `Godot_Template`, а не `Сам проект/Godot_Template`, как в Life_Operator/Godot_Template.
На это и опирается разница команд ниже (subtree push с пробелом/без).

## 2. Ветки в Godot_Template (шаблон)

| Ветка | Что это | Кто пишет |
|---|---|---|
| `Stable` | Открыта потребителям. Только слияние из `Beta` или точечный фикс бага. | Ведущий шаблона |
| `Beta` | Куда стекаются новые фичи (из `alpha/*` и приёмных веток). | Ведущий шаблона |
| `alpha/<имя>` | Личная ветка разработчика, работающего прямо в шаблоне. | Разработчик |
| `Life_Operator`, `Power_struggle` | Приёмные code-only ветки — черновики правок, попутно сделанных внутри проекта-потребителя. Не готовый код, руками разбирается и переносится в `Beta`. | Через `subtree push` из проекта |
| `export/Stable`, `export/Beta` | Code-only срезы `Stable`/`Beta`, которые реально тянут потребители. Обновляются вручную. | Ведущий шаблона |

Прямая разработка фич сразу в `Stable` не ведётся — только через `Beta`.

## 3. Регулярный чек-лист (перед началом и в конце работы)

Перед тем как начать работать в любом из трёх проектов:

```bash
git status                 # нет ли забытых незакоммиченных изменений с прошлого раза
git fetch --all --prune    # подтянуть, что изменилось на GitHub, и убрать протухшие ветки
git log HEAD..origin/<текущая ветка> --oneline   # есть ли что подтянуть (git pull)
git log origin/<текущая ветка>..HEAD --oneline   # есть ли что отправить (git push)
```

В конце работы:

```bash
git status                 # всё ли закоммичено
git push                   # отправить локальные коммиты на GitHub
```

Если `git log HEAD..origin/...` показывает коммиты — значит на GitHub есть то, чего нет
локально (например, правки, сделанные из другого чата/сессии/устройства). Сначала
`git pull` (или `git merge origin/<ветка>`), потом продолжать работу.

## 4. Работа в проекте-потребителе (Life_Operator, позже Power_struggle)

Подтянуть новое из шаблона:

```bash
git fetch godot-template export/Stable
git subtree pull --prefix="Сам проект/Godot_Template" godot-template export/Stable --squash
```

(для Power_struggle — `--prefix=Godot_Template`, путь без пробела, репозиторий там уже
существует и настроен).

Отправить правку общего кода обратно в шаблон:

- Путь без пробела (Power_struggle): `git subtree push --prefix=Godot_Template godot-template <ИмяПроекта>`
- Путь с пробелом (Life_Operator, из-за бага git-subtree с пробелом в пути) — вручную:

```bash
git fetch godot-template <ИмяПроекта>
TREE=$(git rev-parse "HEAD:Сам проект/Godot_Template")
NEWCOMMIT=$(git commit-tree "$TREE" -m "Godot_Template/ из <ИмяПроекта>" -p FETCH_HEAD)
git push godot-template "$NEWCOMMIT":<ИмяПроекта>
```

`<ИмяПроекта>` = `Life_Operator` или `Power_struggle`.

## 5. Работа в самом шаблоне (Godot_Template)

Проверить, что накопилось в приёмных ветках (после `git fetch`):

```bash
git log Beta..origin/Life_Operator --oneline
git log Beta..origin/Power_struggle --oneline
```

Если локальная ветка `Life_Operator`/`Power_struggle` отстаёт от `origin/...` (после чужого
push из другого чата/сессии) — подтянуть её:

```bash
git branch -f Life_Operator origin/Life_Operator
git branch -f Power_struggle origin/Power_struggle
```

Перенести удачное из приёмной ветки в `Beta` (subtree-merge, т.к. приёмная ветка code-only,
а `Beta` — весь проект):

```bash
git checkout Beta
git merge -X subtree="Сам проект/Godot_Template" Life_Operator --allow-unrelated-histories
```//скорректировать при необходимости под конкретный случай

Обновить `export/Stable`/`export/Beta` после правок на полной ветке (subtree split не работает
из-за бага с пробелом в пути):

```bash
TREE=$(git rev-parse "Stable:Сам проект/Godot_Template")
NEWCOMMIT=$(git commit-tree "$TREE" -m "Godot_Template/ из ветки Stable" -p export/Stable)
git branch -f export/Stable "$NEWCOMMIT"
git push origin export/Stable --force
```

## 6. Задуманная модель потока изменений (по описанию автора проекта, версия 2)

### 6.1. Внутри Godot_Template

1. Любое изменение сразу попадает в `alpha/<источник>`. После проверки и исправления багов
   из неё отправляется запрос на слияние в `Beta`.
2. `Beta` — точка сборки: сюда стекаются все `alpha/*`, здесь идёт проверка и правки, чтобы
   всё сошлось без конфликтов. Из `Beta` — отправка в `Stable`.
3. После того как изменение попало в `Stable` — создаётся запрос на слияние **обратно** в
   каждую `alpha/*` (замыкающий шаг: `alpha` не должна расходиться с тем, что уже стабильно).

На этом цикл `alpha → Beta → Stable → alpha` внутри самого Godot_Template закончен.

### 6.2. Со стороны Power_struggle / Life_Operator (проектов-потребителей)

Для проектов действует **только** ветка `Stable` шаблона (через `export/Stable` — см. п. 4) —
никакого прямого использования `Beta`/`alpha` шаблона внутри проекта.

1. Любое изменение файлов в папке `Godot_Template/` внутри проекта — это ПРЕДЛОЖЕНИЕ правки
   в сам шаблон: оно уходит в `alpha/<Проект>` (напр. `alpha/Power_struggle`) в репозитории
   Godot_Template. Применить это изменение (обновить локальную `Godot_Template/` у себя в
   проекте) можно только после того, как оно пройдёт весь цикл 6.1 и попадёт в `Stable`
   (→ `export/Stable` → `subtree pull`) — то есть нельзя просто отредактировать
   `Godot_Template/` у себя и продолжать работать поверх непроверенной правки.
   Дополнительно: в проекте можно завести отдельную папку `Godot_Template_<Проект>`
   (например `Godot_Template_PowerStruggle`) — классы, которые НАСЛЕДУЮТ классы шаблона и
   переопределяют/дополняют их под нужды проекта, не трогая сам `Godot_Template/`. Именно
   изменения в этом слое (когда они логически относятся к общей функциональности, а не
   только к этому проекту) и есть то, что уходит в `alpha/<Проект>` на постоянной основе.
2. Изменения, которые НЕ затрагивают `Godot_Template/` (игровая логика, экраны и т.п.),
   живут в собственном цикле `alpha → Beta → Stable` внутри самого проекта и с шаблоном
   никак не синхронизируются.

### ✅ Подтверждено пользователем

- Приёмные ветки в Godot_Template переименовываются: `Life_Operator` → `alpha/Life_Operator`,
  `Power_struggle` → `alpha/Power_struggle`. Точные команды переименования — см. раздел 9
  (ждут «Применяй»).
- Паттерн `Godot_Template_<Проект>` подтверждён: `Godot_Template/` — 1:1 копия ветки `Stable`
  шаблона (никогда не редактируется напрямую), а `Godot_Template_<Проект>/` — слой
  наследования/переопределения под нужды проекта; именно из него уходят предложения в
  `alpha/<Проект>`.

## 7. Возможная автоматизация (предложение — не внедрено, нужно ваше «Применяй»)

Ничего из этого не настроено само — это варианты, что можно сделать через GitHub Actions,
если решите автоматизировать процесс из раздела 6:

- **PR alpha → Beta с автопроверкой**: workflow, который на каждый Pull Request в `Beta`
  автоматически открывает Godot-проект в headless-режиме (`godot --headless --import`/
  `--check-only`) и гоняет базовый lint/тесты (например `gdlint`, если он уже используется) —
  чтобы конфликт/поломка кода была видна ещё до слияния, а не постфактум.
- **Автообновление `alpha/*` после слияния в `Beta` и после `Stable`**: workflow,
  срабатывающий на `push` в `Beta` и отдельно на `push` в `Stable`, который проходит по всем
  веткам `alpha/*` и мержит в них свежую ветку (fast-forward либо merge-commit; если
  конфликт — не мержить автоматически, а открыть Issue или PR с пометкой «нужен ручной
  мердж») — закрывает оба места из модели 6.1, где нужен обратный мердж в `alpha`.
- **Автогенерация `export/Stable`/`export/Beta`**: workflow на `push` в `Stable`/`Beta`,
  который сам выполняет ту самую ручную процедуру `commit-tree` из раздела 5 (она как раз
  типовая и легко переносится в скрипт/Action) — снимает с вас необходимость делать это
  руками после каждого изменения.
- **Уведомление потребителей об обновлении шаблона**: когда `export/Stable` обновился,
  `repository_dispatch`/`workflow_dispatch` может открыть PR с уже выполненным
  `subtree pull` в Life_Operator и Power_struggle — вы просто проверяете и мержите, а не
  вспоминаете вручную, что «шаблон обновился, надо бы подтянуть».
- **Автоматизация push-back в приёмную ветку**: workflow в самом проекте-потребителе,
  срабатывающий на `push` в `main`, который проверяет — задет ли в коммите путь
  `Godot_Template/` (или `Сам проект/Godot_Template/`) — и если да, сам выполняет
  `subtree push` (или ручной `commit-tree`-обход для путей с пробелом) в приёмную ветку
  шаблона, вместо того чтобы держать это в голове как отдельный ручной шаг.

- **Пуш из `Godot_Template_<Проект>` в `alpha/<Проект>`**: workflow в проекте-потребителе на
  `push` в `main`, который смотрит, задета ли папка `Godot_Template_<Проект>/`, и если да —
  сам собирает и пушит эту правку как коммит в `alpha/<Проект>` в репозитории шаблона (аналог
  push-back из раздела 4, но в `alpha/*`, а не напрямую в приёмную ветку). Изменения
  выделяются отдельно по каждому классу/методу (не одним блоком), чтобы предлагать их
  на слияние по пунктам, а не общей кучей.
- **Сверка `Godot_Template_<Проект>` после `subtree pull`**: после того как в проект
  подтянулась обновлённая `Godot_Template/`, скрипт проходит по всем переопределениям в
  `Godot_Template_<Проект>/` и для каждого сравнивает его текущий код с тем, что теперь лежит
  в обновлённой `Godot_Template/`:
  - **Точное совпадение** (переопределение стало не нужно, т.к. шаблон теперь делает то же
    самое) → автоматически: удалить переопределение из `Godot_Template_<Проект>/` и
    заменить все обращения в коде проекта с `Godot_Template_<Проект>.Класс` на
    `Godot_Template.Класс` (обычный project-wide find-and-replace по имени класса/пути).
  - **Нет точного совпадения** (шаблон изменился, но по-другому, или переопределение всё ещё
    нужно) → ничего не трогать автоматически, а добавить пункт в список на подтверждение
    (например, отдельный `.md`-чеклист или Issue) — человек решает по каждому пункту отдельно
    перед тем, как что-то менять.

## 8. Технологический стек для автоматизации

Три слоя, каждый — то, для чего он лучше всего подходит:

- **GitHub Actions (YAML)** — только «дирижёр»: реагирует на события (`push`, `pull_request`,
  `workflow_dispatch`), решает, что запустить, и передаёт результат дальше (комментарий в PR,
  новая ветка, Issue). Сам он логику не пишет.
- **Обычные команды git/bash** — там, где логика тривиальна и это буквально то, что уже
  описано в разделах 4–5 (fetch, `subtree pull`/`push`, `commit-tree`, `branch -f`, merge) —
  не нужен отдельный язык программирования, это одна-две строки в workflow.
- **Python** — там, где нужна настоящая логика: сравнение файлов/методов между
  `Godot_Template_<Проект>` и обновлённой `Godot_Template` (раздел 7, «Сверка»), генерация
  списка на подтверждение, project-wide замена ссылок на класс. GDScript/Godot для этого не
  подходит — редактор Godot не предназначен для CI-автоматизации и не имеет удобного доступа
  к git/GitHub API; class в Godot имеет смысл только как отдельная, опциональная штука —
  например, кнопка в редакторе для разработчика, который хочет руками дёрнуть проверку, не
  выходя из Godot, но не как основа автоматизации.

Итого: **GitHub Actions как оркестратор + git/bash для рутинных операций + Python для
сравнения/сверки кода**. GDScript-класс — опционально, потом, как удобство поверх этого.

Всё это требует файлов `.github/workflows/*.yml` (и Python-скриптов) в соответствующих
репозиториях — могу
подготовить черновики, если решите, что конкретно из списка внедрять.

## 8. Частые ошибки и на что обращать внимание

- **Пробел в пути** (`Сам проект/Godot_Template`) ломает `git subtree split` и
  `git subtree push` — только ручной вариант через plumbing-команды (раздел 4/5 выше).
- **⏰ Напоминание (по вашей просьбе)**: `main` должен уступить место `Stable` в качестве
  ветки по умолчанию на GitHub для Godot_Template — на момент этого черновика ещё не
  переключено (HEAD репозитория на GitHub всё ещё указывает на `main`, хотя вся реальная
  работа в `Stable`). Если вы не поменяли это сами — сделайте это (Settings → Branches →
  default branch = `Stable` на GitHub), при следующем «Применяй» я вам об этом напомню ещё раз.
- **Приёмные ветки не самообновляются локально** — после `git fetch` обновляется только
  `origin/Life_Operator`/`origin/Power_struggle`, а локальная ветка того же имени остаётся на
  месте, пока её не подвинуть (`git branch -f ...`). Не забывать про этот шаг перед разбором
  накопленных правок.
- **Не коммитить в шаблон специфичный для проекта код** (игровая логика Power_struggle,
  экраны Life_Operator и т.п.) — это должно жить рядом, не внутри `Godot_Template/`.
- Периодически `git fetch --prune`, чтобы не копились ссылки на переименованные/удалённые
  ветки (например, старые русскоязычные названия веток).
